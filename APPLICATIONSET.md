# ApplicationSet learning notes (what we did)

This document is the lab we actually ran: Helm charts in Git, Argo CD on one cluster, apps on two other clusters, generated by **one ApplicationSet**.

Repo: https://github.com/jagadish1010/e-commerce-helm

Single-cluster install, UI port-forward, and first `argocd app create` are in [ARGOCD_SETUP.md](ARGOCD_SETUP.md). Helm overlay (`--set env=`) is in [README.md](README.md).

## 1. Words we used (keep these straight)

| Thing | What it is |
|---|---|
| **Helm chart** | `payments/` and `shipping/`. Git is the source of truth. |
| **Application** | One Git path → one cluster + namespace. Example: `payments-dev`. |
| **ApplicationSet** | A factory. One YAML that **creates many Applications**. |
| **AppProject** | Guardrail: which Git repo, clusters, and namespaces are allowed. |
| **App-of-apps** | One **Application** whose `path:` is `argocd/`. Argo CD then syncs the ApplicationSet YAML from Git. Optional; we used `kubectl apply` for the AppSet instead. |

We did **not** install Argo CD on DEV and QA. One Argo CD, two **registered** clusters.

```text

                     clone + Helm --set env=
                                |
```

## 4. How the live ApplicationSet works

File: [`argocd/ecommerce-appset-clusters.yaml`](argocd/ecommerce-appset-clusters.yaml)

**Matrix generator** = every service × every matching cluster.

1. **List:** `payments`, `shipping`
2. **Clusters:** every cluster secret labelled `ecommerce=true`
3. From that cluster’s `env` label (`dev` or `qa`) it fills:
   - Application name: `{{service}}-{{env}}` → `payments-dev`, …
   - Helm: `--set env={{env}}`
   - Namespace: `ecommerce-{{env}}`
   - Destination **server:** that cluster’s API URL (not `kubernetes.default.svc`)

The management cluster is **not** labelled, so nothing is deployed onto `210`.

Adding a third env later: `argocd cluster add … --label ecommerce=true --label env=stage`. This YAML does not change.

Other designs (single cluster, hardcoded URLs) are in [`examples/README.md`](examples/README.md).

## 5. Steps we followed

### A. Charts in Git

1. One `values.yaml` per chart; overlay with `--set env=dev|qa`.
2. Push `payments/` and `shipping/` to GitHub (PAT, not GitHub password).
3. Argo CD clones Git. It cannot see files only on the Mac.

### B. Argo CD on the management cluster

1. `kubectl create ns argocd`
2. Official `install.yaml`. If CRDs fail with “too long” annotation:  
   `kubectl apply --server-side --force-conflicts -n argocd -f …/install.yaml`
3. Wait for `argocd-server`, repo-server, application-controller, **applicationset-controller**.
4. Confirm CRD: `kubectl get crd applicationsets.argoproj.io`

If the ApplicationSet controller crash-looped after a partial install:

```bash
kubectl --context '10_196_102_210:6443' -n argocd rollout restart deploy/argocd-applicationset-controller
```

### C. UI and CLI (port-forward)

Argo CD Service is ClusterIP. Lab NodePort was reset from the Mac. Use port-forward.

```bash
kubectl --context '10_196_102_210:6443' port-forward -n argocd svc/argocd-server 8080:443
```

Browser: **https://localhost:8080** (self-signed cert).

Admin password:

```bash
kubectl --context '10_196_102_210:6443' -n argocd \
  get secret argocd-initial-admin-secret -o jsonpath='{.data.password}' | base64 -d
echo
```

```bash
argocd login localhost:8080 --username admin --insecure
```

`login` must run on the **same machine** as port-forward. SSH `-L 8080:localhost:8080` if the browser is on the Mac and forward is on the VM.

Port 8080 already in use:

```bash
# Linux VM
fuser -k 8080/tcp
# Mac
kill $(lsof -t -iTCP:8080 -sTCP:LISTEN)
```

### D. First lesson: one Application (same cluster as Argo CD)

`argocd app create payments-dev` with `--dest-server https://kubernetes.default.svc`, `--helm-set env=dev`, automated prune + self-heal. See [ARGOCD_SETUP.md](ARGOCD_SETUP.md).

That proved Git → Helm → pods. We **deleted** those apps before multi-cluster so they would not fight the ApplicationSet.

### E. Merge kubeconfigs on the Argo CD VM

Lab SSH is often `csh`. Use `bash`. Home NFS + `root_squash` blocked writes; use `/tmp`.

Do **not** flatten a kubeconfig onto itself (`KUBECONFIG=file` and `>` that same file empties it). Write `.new` then `mv`.

Contexts we used: management (`10_196_102_210:6443`), `dev`, `qa`.

```bash
bash
export KUBECONFIG=/tmp/kubeconfig-lab
kubectl config get-contexts
```

Register clusters **from the VM** (`argocd cluster add`). Mac TLS to `:6443` failed.

### F. Register DEV and QA

Port-forward running, then:

```bash
argocd cluster add dev --name dev --label ecommerce=true --label env=dev
argocd cluster add qa  --name qa  --label ecommerce=true --label env=qa
argocd cluster list
```

Labels are required. No labels → ApplicationSet generates **zero** Applications.

### G. Apply the ApplicationSet

```bash
kubectl --context '10_196_102_210:6443' apply \
  -f https://raw.githubusercontent.com/jagadish1010/e-commerce-helm/main/argocd/ecommerce-appset-clusters.yaml

kubectl --context '10_196_102_210:6443' get applicationset,applications -n argocd
argocd app list
```

Expected four apps, all **Synced** / **Healthy**:

| Name | Cluster | Namespace |
|---|---|---|
| `payments-dev` | DEV | `ecommerce-dev` |
| `shipping-dev` | DEV | `ecommerce-dev` |
| `payments-qa` | QA | `ecommerce-qa` |
| `shipping-qa` | QA | `ecommerce-qa` |

Proof pods are **not** on `210`:

```bash
kubectl --context dev get pods -n ecommerce-dev
kubectl --context qa  get pods -n ecommerce-qa
kubectl --context '10_196_102_210:6443' get ns | grep ecommerce
```

Last command should print nothing.

### H. UI checklist

1. **Applications** — four green tiles.
2. Open `payments-dev` — destination is the **DEV** API URL, Helm `env=dev`.
3. **Tree** — Deployment / Pods on that cluster.
4. **ApplicationSets** — resource `ecommerce` (if the UI version shows it).
5. **Projects** — `default` until you apply `ecommerce-project.yaml`.

### I. Optional: AppProject

```bash
kubectl --context '10_196_102_210:6443' apply \
  -f https://raw.githubusercontent.com/jagadish1010/e-commerce-helm/main/argocd/ecommerce-project.yaml
```

Then set `spec.template.spec.project: ecommerce` on the ApplicationSet (today it is `default`). Destinations in the project must match `argocd cluster list` URLs.

### J. Optional: app-of-apps

[`bootstrap/root-app.yaml`](bootstrap/root-app.yaml) is an Application named `ecommerce-root` with `path: argocd` and destination **management** (`kubernetes.default.svc`). Apply it **once** with kubectl. After that, Git changes under `argocd/` sync themselves.

Do **not** put `root-app.yaml` inside `argocd/` or it would try to sync itself forever.

Only keep **one** live ApplicationSet under `argocd/` (we moved the rest to `examples/`).

## 6. GitOps behaviour we learned

- **HEAD** = latest commit on the default branch.
- **Auto-sync** applies Git without clicking Sync.
- **Prune** deletes cluster objects removed from Git.
- **Self-heal** reverts manual `kubectl` edits.
- **Rollback** in the UI pins an old revision and **turns auto-sync off** until you enable it again.
- `replicaCount` lives under `.Values.config` in these charts, not the Helm default top-level key.

QA **Progressing** with Ingress enabled meant there was **no** Ingress controller. Ingress is disabled in Git for this lab.

## 7. Lab gotchas (short)

| Problem | Fix |
|---|---|
| GitHub push with account password | PAT or `gh auth login` |
| `sudo export` / `sudo kubectl` | `sudo` drops user `KUBECONFIG` |
| csh `2>/dev/null` | `cp: target '2'` — use bash |
| ApplicationSet CRD missing | Server-side apply of install.yaml; restart controller |
| `argocd` CLI to 8081 | Port-forward is 8080 |
| PermissionDenied deleting apps | `kubectl -n argocd delete application …` |
| Four AppSets in `argocd/` | Keep one live file; rest in `examples/` |

## 8. Day to day

1. Change `payments/` or `shipping/` (or `env` overlay).
2. `git commit` and `git push origin main`.
3. Argo CD updates the matching Applications. Do not `helm upgrade` those releases unless debugging.

New cluster: register it with labels; ApplicationSet creates `payments-<env>` and `shipping-<env>` automatically.
